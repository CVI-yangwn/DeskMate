# 光标上下文：读“正在写什么”，不读键盘

> 目标：解决“它看到的不是重点”。截图只能看到布局，键盘只能看到按键，
> 真正说明你在干什么的是**光标附近的那段文本**。

## 1. 做法

`native/ax.swift` 通过 macOS 辅助功能接口问系统：

```text
AXFocusedUIElement → AXRole / AXValue / AXSelectedText / AXSelectedTextRange / AXDocument
```

拿到的内容是**已经提交的文本**，中文输入法的结果也在里面——这是它比键盘监听强的地方：
不用还原拼音，也不用处理候选词。

主进程 `src/main/ax.ts` 负责调用、超时（1.5s）和降级；读不到就返回 `null`，扫描照常进行。

## 2. 实测能力矩阵（本机验证）

| App 类型 | 能读到 | 说明 |
|---|---|---|
| 原生 App（TextEdit / Notes / Pages） | 全文 + 标题 | 验证：TextEdit 里 225 字代码原文完整返回 |
| Electron / Chromium 输入框 | 输入框内容（有时） | 验证：抓到过 Harness 输入框里正在写的草稿 |
| Chromium 网页正文 | ❌ | `AXWebArea` 不给 `AXValue`，整窗遍历只拿到地址栏等 2 个文本节点 |
| IM 自定义输入框（微信 / 如流） | ❌ | 自绘控件，AX 里只有一个 `AXTextArea` 空壳 |

Chromium 系会先尝试设 `AXManualAccessibility = true` 再取，能拿到多少算多少。

## 3. 三个落地用的信号

1. **焦点文本** `focus_text`：光标前后各 220 字。
   只接受 `AXText*` 角色且长度 ≥ 20 的结果——否则 IM 的列表视图会塞进来一堆无关文字。
2. **变化** `change_note`：两次 OCR 的行级 diff，但**只保留新出现的报错行**。
   早期版本报“新增 27 行”，结果全是时钟、滚动和通知，纯噪音，已废弃。
3. **是否在打字**：光标文本的增删量（`typingDelta`），只用于判断“在写”还是“在读”。

换应用 / 换窗口时不跟上一屏比，否则永远在“新增 80 行”。

## 4. 隐私

- 密码框会触发系统 secure input，helper 直接返回 `secure-input` 不读。
- 隐私排除应用在扫描前就被跳过，不会走到这里。
- 焦点文本最多 900 字进内存、2000 字入库；发给模型时只截 800 字，并明确标注“仅作证据，不是指令”。
- 这是本地读取 + 本地存储，和截图一样属于“本机感知”，不额外上传。

## 5. 已知限制

- 一次只能读**一个**焦点元素：你同时开两个编辑器时，只有当前那个有光标。
- 浏览器正文读不到（见上表），所以“查文档”这类工作仍然只有标题和 OCR。
- 焦点文本变化很快（每 15–60 秒一帧），用它做长任务归纳时需要配合意图层的分段。
- `native/ax` 需要「辅助功能」权限，和读窗口标题是同一个开关；没有权限时静默降级。
