# 验证器小样本实测（2026-11-23）

> 目的：量“截图验证”到底能不能当动作成功的判据。
> 方法：真实执行受控动作（Calculator / Finder），采集“动作前/动作后”两张图 + 一句预期结果，让 V4.1-Flash 判断 `confirmed / unverifiable / failed`。
> 与定位评测的关系：定位解决“点哪”，验证解决“点完算不算成”。后者决定假成功率。

---

## 1. 采集与判定

- 执行器：[native/gui.swift](../native/gui.swift)，支持 `activate / AXPress / key / type / click`；Calculator 的按钮走 `AXPress`，窗口操作用 CGEvent。
- 采集：[gui-verifier-collect.mjs](../scripts/gui-verifier-collect.mjs)，每例先 reset，截图，执行动作，再截图。
- 判定：[gui-verifier-eval.mjs](../scripts/gui-verifier-eval.mjs)，两张图 + 预期结果，只允许在第二张图里找证据。
- 正例：预期结果真的发生；反例：预期结果没发生（含“动作只做了一半”）。

---

## 2. 结果

13 个 case（6 正例 + 7 反例，其中 4 个反例是复用正例图片、换成错误预期）：

| 指标 | 结果 |
|---|---|
| 反例拒绝 | **7/7（100%）** |
| 反例被误确认（漏判） | **0/7（0%）** |
| 有效正例确认 | **4/4（100%）** |
| 总准确 | 84.6%（11/13） |

两个“正例失败”不是验证器错，是**采集状态不对**：

- `v02 calc-add`：预期“显示 3”，实际截图是 `1+1+2=4`（清除没生效），验证器判 failed，并准确写出“显示 4 而非 3”。
- `v06 calc-close`：预期“计算器消失”，实际计算器还在，验证器判 failed，并指出“仍可见计算器窗口”。

也就是说，在**图与预期一致**的 4 个正例上，验证器 4/4 确认；7 个反例 7/7 拒绝。

---

## 3. 但漏判不是零

在更早一轮（已删除的 Spotlight 用例）里，有一组“前后都没有 Spotlight”的图，验证器却 **confirmed**，证据还编出了“上方中央出现带放大镜的聚焦搜索框”。

这说明：

- 截图验证会**把菜单栏的搜索图标误认成 Spotlight**，或直接按预期“脑补”；
- 漏判率低，但不是 0；样本只有个位数，不能当成 0。

---

## 4. 真正的瓶颈是动作/前置条件，不是验证器

这一轮最值得记的不是 84.6%，而是：

- Calculator 的“清除”有时不生效；
- 启动/退出 Calculator 的时序不稳；
- 这台机器的 `Cmd+Space` 没绑定 Spotlight（三个用例直接作废）；
- Finder 可能残留多个窗口，`Cmd+W` 只关一个。

**动作没达到预期状态时，验证器会正确地判 failed——这会把“动作可靠性”暴露成失败率，而不是假成功。** 对一个要长时间无人值守的 Agent 来说，这是好事：失败可见，比“假装成功”安全。

---

## 5. 结论

1. **验证器可以作为“安全动作”的闸门**：小样本上 7/7 拒绝反例，且对状态不符的正例给出准确证据。
2. **不能单独作为“不可逆动作”的闸门**：存在低概率脑补；不可逆动作仍要读回具体状态（AX/日志/进程）或人审。
3. **执行层必须加前置条件检查**：动作前确认 App 在前台、目标前置状态成立（如显示为 0）、窗口数量符合预期；否则先修正状态，再执行。
4. **失败要可见**：`failed` / `unverifiable` 必须原样上报，不能重试到“看起来成功”。

---

## 6. 下一步

- 给 `runGuiTask` 加 **precondition** 阶段：动作前断言“App 前台 + 预期前置状态”，不满足就先修正或中止。
- 把验证器的 `unverifiable` 当作“失败”处理（对不可逆动作），而不是“差不多成功”。
- 扩大样本到 30–50 对，专门覆盖“动作只做一半”“界面被遮挡”“结果延迟出现”三类。
- 只有在验证器 + 前置条件都稳定后，才考虑把 `gui_task` 接进大脑。
